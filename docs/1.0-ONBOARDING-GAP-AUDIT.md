November 10, 2026 (Central). Maintainer-requested audit and accepted task scope;
the proposed commands below are design examples, not implemented CLI options.

## What was checked

Compared 16 live pages at [weftlet.crowdpigeon.org](https://weftlet.crowdpigeon.org/)

public pages and toolkit source; private site automation/configuration is omitted.

0.10 candidate; they are not new adapters we still need to design from scratch.

storage ignore entry. It does not install the shipped skill, register MCP, or
install CI examples. Users currently assemble these steps manually. That is an
onboarding gap worth closing before 1.0.

## How model-assisted setup should work

An MCP connection lets a development agent query Weftlet. It does not currently
give the Weftlet process a general-purpose session to call back into that agent.
There are two useful ways to deliver assistance:

1. The installed project skill guides the user's already-running development
   agent through setup planning and the deterministic setup commands. This uses
   the developer's existing agent session and normal edit review.
2. An opt-in toolkit setup assistant invokes the configured CLI/provider to
   return a structured setup plan. It can understand an existing monorepo or CI
   pipeline, then hand proposed edits to the same deterministic writer.

Reuse provider authentication, discovery, cancellation and bounded output where
appropriate. Semantic extraction currently returns graph assertions; it is not
a workflow-editing contract. Add a distinct typed plan/patch contract and schema
validation instead of treating arbitrary model text as executable instructions.

Basic skill/config/workflow template installation needs no AI. The assistant
should focus on repository-specific decisions: identifying relevant source
directories, integrating existing jobs and explaining ambiguous source roles.
It may suggest authority patterns; only the user's confirmed choice makes them
governing. Keep setup usable with no model available.

Proposed interaction, not current CLI syntax:

```text
weftlet init
  Select development clients: Codex / Claude Code / OpenCode
  Install project skill and configure MCP: yes / customize / skip
  Select documents and governing-source patterns
  Add CI: PR checks / trusted generation / skip
  Optional: use configured assistant to adapt existing setup
  Review planned changes → apply → verify

weftlet setup --client claude --dry-run
weftlet setup --client claude --apply
```

Changing a planned file between preview and apply must trigger a fresh plan,
not overwrite the user's concurrent edits. Install/update owns only its own
files or clearly bounded sections. User-selected integration should avoid
repetitive confirmation while still presenting the actual file diff and model
scope before applying work with those effects.

## Keep in their existing later milestones

- Hosted multi-user approvals, claim review, document backfill and source writeback.
- Figma/Trello/GitHub Projects connectors and remote source revision/permission lifecycle.
- Managed AI billing, subscription/OAuth work beyond each supported provider contract.
- Separate architecture packages and policy-generated architectural skills.
- Authenticated hosted graph service/database deployment and continuous synchronization.

Architecture analysis, local graph browsing and several mapping mechanisms
already exist; their larger follow-ups should not erase those current benefits
from the docs or become unbounded prerequisites for 1.0.
